### 1.1 §3.2 的修法必须同时改两处——这一点它说对了

它明确警告"只放开拒收会更糟":`normalizeEreClasses` 有同一个盲点,只改 `firstPerlClass` 的话,
`[[:alpha:]\d]` 会被原样交给 `CompilePOSIX`,Go 把类内的 `\d` 当**数字类** ——
从"响亮报错"变成"**静默少匹配**"。这个判断是对的,所以修法是抽**唯一一份** `classEnd()`,
两个函数各自调用它。

## 二、唯一的分歧:§3.1 的幅度

复审给的数字是"3000 项多付 2.1s",而我实测同一件事:

```
修前:winbash ls 129ms   winbash ls -l 155ms   真 bash ls -l 223ms
修后:winbash ls  20ms   winbash ls -l  28ms
```

**它的机制判断完全正确**(`DirEntry.Info()` 在 Windows 上走 `WIN32_FIND_DATA` 缓存、
`os.Stat` 是一次全新的 `GetFileAttributesEx`;短格式根本不看 `info`,那条路径上的 stat 是纯浪费),
而且修复**确实带来 6.5× 的提速**。但"2.1s"这个绝对值我在热缓存下复现不出 —— 它给的
4574× 微基准比值可能来自另一台机器/另一种缓存状态。

**为什么仍然要修**:与快不快无关。"短格式的 `writeLsEntry` 从不读 `info`"意味着那条路径上的
每一此 stat 都是**纯浪费**,这一点在冷缓存、网络盘、杀毒软件挂钩的环境下会放大。而且我上一轮
为把 `.`/`..` 并进统一排序,顺手把 `e.Info()` 换成了 `os.Stat` —— 这是个**不必要的退化**,
不该因为"本机测不出来"就留着。

## 五、仍然没做的(记账,不是遗漏)

| 项 | 为什么 |
|---|---|
| 协议版本号 | 目前靠"字段可选 + 缺凭据拒绝"兜住;等真要改帧格式(如流式输出)时再上 |
| daemon 的 stderr 重定向到日志文件 | 意见合理,但要先决定日志位置与轮转策略 |
| `ls` 的 locale collation | 复审自己也标了"需确认":本机 bash 是 `C.UTF-8`,collation 即码点序;换成 `en_US.UTF-8` 的 bash 时 GNU ls 可能不同。**这是一个还没测过的真实缺口** |
| CI | 仓库是 `git subtree split -P winbash` 拆出来的,根目录只有 `winbash/`,而 GitHub 只认仓库根的 `.github/` |

最后一条要特别说:`ls` 的排序在**不同 locale 下**是否仍与真 bash 一致,目前**没有**任何语料覆盖。
本轮的 `!x . ..` 这条只覆盖了码点序。这是下一个值得钉的地方 —— 而钉它的正确做法和 §3.2 一样:
**把真 bash 的输出机器生成成 golden,而不是手写期望值**。
