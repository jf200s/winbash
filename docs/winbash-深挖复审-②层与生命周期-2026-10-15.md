## 二、存在的问题

### 2.1 【建议】`--idle` 对自动拉起的 daemon 静默失效

**位置**：`internal/client/client.go:301`

```go
cmd := exec.Command(exe, "--serve", "--endpoint", endpoint)
```

**成因**：`spawnDaemon` 只转发 `--serve` 与 `--endpoint`，**没有转发 `--idle`**。自动拉起的 daemon
因此永远用 `main.go:52` 的默认值 30 分钟。使用者显式写的 `--idle` 被静默丢弃，无任何提示。

**实测对照**：

```
A) winbash --idle 3s -c 'echo start'      （client 自动拉起 daemon）
   等 6s 后：winbash 进程 = 1  端口文件 = 仍存在   ← 没退

B) winbash --serve --endpoint X --idle 3s  （手动 --serve，--idle 真的传进去）
   等 8s 后：winbash 进程 = 0  端口文件 = 已删除   ← 正常退出，pwsh 也回收了
```

A 与 B 的差别只在参数有没有传进去 —— 空闲退出的**机制本身是对的**，丢的是转发。

**影响**：README 把 `--idle` 列为 CLI 参数（默认 30m）。想让 daemon 短命的使用者（例如跑完就走、
或不想在机器上留常驻进程）设了也不会生效，而且**没有任何反馈**。属于"文档承诺了、实现没转发"。

**修改建议**（择一）：
- 转发：`spawnDaemon(endpoint string, idle time.Duration)`，把 `--idle` 拼进 argv。改动最小，
  但要求 `oneShot`/`dial`/`ensureDaemon` 一路把 idle 传下去（它们现在只传 endpoint）。
- 或者：文档层面承认 `--idle` 只作用于手动 `--serve`，并在 CLI 检测到"自动拉起且指定了非默认 idle"
  时打一行提示。

**验收**：`winbash --idle 3s -c 'echo x'` 后等待 5s，daemon 进程应已退出且端口文件已删除。

### 2.2 【建议】`looksLikeMissingPath` 大小写敏感，漏掉最常见的 `no such file`（小写）

**位置**：`internal/errs/errs.go:72-85`

```go
for _, s := range []string{
    "No such file", "cannot change to", "cannot find", "not found", "does not exist",
} {
    if strings.Contains(raw, s) { return true }
}
```

**成因**：全部是**区分大小写**的子串匹配。而 `no such file or directory` 在大量工具里是**小写**开头的
（Node.js 的 `ENOENT`、许多 Go/Python 库、以及部分 GNU 工具在非首句位置）。

**实测对照**（同一个 POSIX 路径 `/c/definitely/not/here`，同一个 winbash）：

| 外部工具 | 错误文本 | 翻译是否触发 |
|---|---|---|
| `git -C /c/nope status` | `fatal: cannot change to '/c/nope': No such file or directory` | ✅ 触发 |
| `node -e "…readFileSync('/c/nope')"` | `Error: ENOENT: no such file or directory` | ❌ **未触发** |

两条都是"外部工具收到 POSIX 路径"这个完全相同的坑，但因为大小写，一条给了可操作提示、一条没有。
而 `TranslateKnownTrap` 存在的唯一理由，就是**在这类场景下把 AI 的下一步动作说清楚**。

**修改建议**：把匹配改成大小写不敏感（最省事）：

```go
low := strings.ToLower(raw)
for _, s := range []string{"no such file", "cannot change to", "cannot find", "not found", "does not exist"} {
```

注意 `"no such file"` 与已有的 `"not found"` 不冲突；改小写后需要复核是否误伤（例如工具输出里恰好
提到 "not found" 但不是路径问题——这种情况本来就会误伤，与大小写无关）。

**验收**：`node -e "require('fs').readFileSync('/c/nope')"` 在 winbash 里应带出"路径是 POSIX 写法"的提示。

**附带**：`errs` 包只有 57.1% 覆盖率（全仓最低），原因是 4 个测试只覆盖了 bash/WSL 那一条分支；
`hasPosixPathArg`、`hasSingleSlashFlag`、`looksLikeMissingPath`、`isLetter` 全部 0%。
补上面两个场景的用例即可把这个包拉起来。

### 2.3 【建议】`grep` 未实现 GNU 的"二进制文件"输出策略

**位置**：`internal/builtins/grep.go`（`grepFile` / `grepStream`）

**实测**（受控二进制文件，40 段 × 20 字节，字母表 `{x, y, \n, 0xFF, NUL}`）：

```
真 grep  : Binary file C:/…/nocr.bin matches     ← 抑制内容，只给一行提示（70 字节）
winbash  : yM-^?xx^@x…                            ← 把含 NUL/0xFF 的原始字节直接吐出来
```

**重要澄清（避免误判）**：winbash 的**匹配语义是对的**。用 `grep -a` 强制真 grep 按文本处理后，
两边都是 **87** 行匹配，逐行行号集合**完全一致**；`wc -l` 两边同为 157。差异只在**输出策略**：
GNU grep 检测到 NUL 就切到二进制模式、只打一行 `Binary file … matches`，winbash 没有这个分支。

（我一开始量到"真 grep -c 给 116、winbash 给 87"的计数差异，追下去发现是 GNU grep 自己在二进制
模式下的计数方式与文本模式不同 —— 用 `-a` 对齐后两边相同。这个计数差异不是 winbash 的问题。）

**影响**：对一个面向 AI 的 shell，把 NUL 与 0xFF 直接写进输出流是有害的 —— 污染 token、可能破坏
下游解析；而真 bash 的行为是给一行干净的提示。且 **README 全文没有 "二进制 / Binary" 任何字样**，
属未记录的差异。

**修改建议**（择一，都不复杂）：
- 对齐 GNU：在 `grepFile` 里检测行内 NUL，命中则输出 `Binary file <label> matches` 并跳过内容打印；
  `-c` / `-l` / `-q` 保持计数语义不变（GNU 也是这样）。
- 或者：不实现，但在 README 的"已知差异"表里明确写出这一条，并说明为什么（保持二进制可解析？）。

**验收**：`grep x <含 NUL 的文件>` 与真 bash 输出一致；现有 8 条字符类 golden 不受影响。

### 2.4 【需确认】观察到 1 个 pwsh 孤儿，但受控测试未能复现

**现象**：基线里长期存在 1 个 `pwsh.exe`（pid 35004，`C:\Users\Test User\Applications\PowerShell-7\pwsh.EXE`，
启动于 13:31），而当时 `winbash` 进程数为 0 —— 即**父进程已死的孤儿**。

**受控测试（未能复现）**：

```
清理后基线:            winbash=0 pwsh=1
轮1: 跑完②层=1/2  stop后=0/1
轮2: 跑完②层=1/2  stop后=0/1
轮3: 跑完②层=1/2  stop后=0/1
空闲退出（--serve --idle 3s）: 8s 后 winbash=0 pwsh=1 端口文件已删
```

`--stop` 路径 3/3 正确回收（`Session.Close()` → `pwsh.Close()` 生效），空闲退出路径也正确回收。

**判断**：机制本身没问题，孤儿出现在探针脚本相互打断的混乱序列里（多次 `--stop` 与进程查询交叠）。
**不能据此断定有泄漏**，但也不能排除"某些时序下 `Close()` 没跑到"。建议记一笔：在 `--status` 里
带上 ②层引擎的 pid（`sess.EngineStatus()` 目前只报状态文本），这样孤儿是否由某个 daemon 留下
就一眼可查。

**需确认**：我无法重现触发条件，故标"需确认"而非报告为 bug。

- `errs` 的 MSYS 单斜杠分支（`hasSingleSlashFlag`，`errs.go:88`）：因为 winbash **自己接管了 `reg`**，

## 四、小结

本轮没有发现阻塞项。**②层的安全与值保证这两块是扎实的**——注入防护 4/4、值保证 3/3、
二进制保真、长行无截断，这些是项目立身之本，实测都成立。

三处建议按性价比排序：

1. **`--idle` 转发**（2.1）—— 一行参数，但关系到"文档承诺 vs 实际行为"这类最伤信任的落差。
2. **`looksLikeMissingPath` 大小写**（2.2）—— 一行 `strings.ToLower`，能让 Node.js 这类极常见
   的 ENOENT 场景拿到它本该拿到的提示；顺带把全仓最低的 `errs` 覆盖率拉起来。
3. **`grep` 二进制策略**（2.3）—— 要么对齐 GNU、要么写进已知差异表，别让它悬着（现在的状态是
   "与真 bash 不同，且文档没提"）。

探针脚本与临时文件已清理，`git status` 干净。
