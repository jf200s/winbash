# winbash 实测评估

**评估对象**：`winbash.exe`（2026-10-16 09:41 构建）+ 源码 `fcdd1c7`
**方法**：从真 Git Bash 用全路径调 `winbash.exe`，跑 40+ 条真实命令；关键结论一律用**真 `pwsh` / 真 `bash` 做同通道对照**；全量 `go test ./... -count=1`；`icacls` 看端口文件 ACL；`xxd` 看输出字节编码。
**性质**：**只读评估，未改动任何代码**。本文件是本次唯一的产出。

---

## 1. 结论摘要

**可以用，值得留在手上。** 四层路由、错误信息质量、pwsh 冷启动接管这三件事是实的，都有对照证据。但它省的是 **② 层与"不用换语法"** 的时间，**不是 ① 层纯 bash 的提速** —— 这一点与 README 给人的印象有偏差，见 §3.4。

发现 **1 个应当修的实现问题**（stdin 静默吞，§3.1）、**1 处 README 失实**（§3.2）、**1 个架构性限制**（串行，§3.3）。另有 **2 处"看着像 bug、实测正确"**，记在 §4 以免后人误改。

| 维度 | 结论 | 依据 |
|---|---|---|
| 功能正确性 | **良好** | ② 层输出与真 pwsh 逐字节一致（§2.1）；①层 glob 展开与真 bash 一致（§4.1） |
| 边界与异常输入 | **良好** | 未识别的 flag/参数/子命令一律非零退出，无静默忽略（§2.2） |
| 性能与资源开销 | **达标，但定位需修正** | pwsh 接管省 3.7 倍（§2.3）；①层不比真 bash 快（§3.4） |
| 代码可读性 | **良好** | 四层路由在 `classify.go` 一处判定；注释普遍带实测证据与踩坑记录 |

## 2. 实测确认的正面项

### 2.1 ② 层输出与真 pwsh 逐字节一致

`svc list --running` 前 6 行 vs `Get-Service | ? Status -eq Running | Select -First 6 | ConvertTo-Csv`：

```
14.0.24215.1	Running	Automatic        ← winbash
"14.0.24215.1","Running","Automatic"     ← 真 pwsh
```

逐字段相同，**包括 `14.0.24215.1` 这种畸形服务名**（它本是版本号串，混在服务名里）—— 说明列值来自数据本身，不是按名字模式猜的。`reg get`、`ps explorer`、`sys mem/os` 同样；`--json` 给的是**类型化**值（`MemoryBytes: 350633984` 是数字，不是 `"86,488 K"` 字符串），印证 README 的"值保证由 PowerShell 侧 `.ToString()` 完成"。

`svc status Spooler` → `Spooler\tRunning\tAutomatic`（`STATE: 1` 已翻成 `Running`）。

### 2.2 错误一律响亮，退出码分层

| 输入 | 退出码 | 行为 |
|---|---|---|
| `nosuchcmd_xyz` | **127** | 三行式：问题 + 怎么办（含自查命令 `which nosuchcmd_xyz`） |
| `ls --nonexistent-flag` | **2** | `不认识的参数: --nonexistent-flag` + 列出支持的参数 |
| `sys mem --json` | **2** | 明说 JSON 开关在整次调用上（`winbash --json -c 'sys mem'`） |
| `pwsh -Version` | **2** | `不接管这个参数` + 指路原生 pwsh 全路径。**没有静默回落到原生 pwsh** |
| `grep -q zzz go.mod`（无匹配） | **1** | 与真 grep 一致 |

"不认识的 flag 一律报错退出"这条承诺，实测在 ①②层都成立。

### 2.3 pwsh 冷启动确实被吃掉

| 场景 | 实测 |
|---|---|
| 原生 `pwsh -NoProfile -Command Get-Date` × 5 | **2.375s**（≈475 ms/次） |
| 经 winbash `pwsh -c Get-Date` × 5 | **0.644s**（≈129 ms/次） |
| ② 层 `svc status Spooler` × 10（热引擎） | **0.405s**（≈40 ms/次） |

3.7 倍的相对差距是实测的。**但注意**：README 自己已声明"端到端计时在本机测不出信号"（进程创建基线约 700 ms），所以这些数字只在**同一台机器、同一次会话内的相对比较**里有意义，不能当绝对基准引用。

### 2.4 安全加固已生效

```
icacls <端口文件> →  Test User:(R,W)      # 继承已切,仅当前用户
```

端口文件两行（地址 + token），输出编码为 UTF-8 且**与父进程控制台代码页无关**：用 `chcp 936` 的父进程拉起的 daemon，回给客户端仍是干净 UTF-8 字节（`xxd` 验证）。`ipc.Response.Out` 用 `[]byte` 而非 `string`，避免 `json.Marshal` 把非法 UTF-8 静默替换成 U+FFFD —— 二进制管道不被静默损坏这条是落到实处的。

### 2.5 会话状态：`set -e` / `trap` 的持久是真的

| 命令 | 实测 |
|---|---|
| `set -e; echo "applied"` 后，下一条 `false; echo X` | **exit 1 且未打印 X** —— `set -e` 确实跨命令持久 |
| `trap "echo TRAPPED" EXIT` | 打印 `TRAPPED` |

（`cd` / `alias` 不在其列，见 §3.2。）

### 2.6 复合脚本能力可用

命令替换、数组、`[[ ]]`、算术、`while read`、重定向、`set -o pipefail` 全部按预期工作：

```bash
n=$(ls *.go | wc -l); a=(1 2 3); echo "${#a[@]} $((1+2))"; [[ -f go.mod ]] && echo ok
```

② 层输出接 ①/③ 层工具的管道（`svc list --running | wc -l` → 127）也通。

### 2.7 测试与依赖

- `go test ./... -count=1`：**11 个包全 ok**（shell 15.8s、pwsh 9.6s、winmgmt 9.2s、daemon 8.8s）。
- 唯一直接依赖 `mvdan.cc/sh/v3`，间接 `x/sys`、`x/term` —— 与 README 声明一致。
- 约 10.9k 行 Go，测试文件占比高（`grep.go` 600 行对应 4 个 `grep_*_test.go`）。

## 3. 实测发现的问题

### 3.1 【应修】stdin 被静默吞掉，且退出码为 0

```bash
$ printf 'hello-from-stdin\n' | winbash.exe -c 'cat'
（无输出）   exit=0
```

**根因**（`internal/shell/shell.go:133`）：`interp.StdIO(bytes.NewReader(nil), ...)` 把 stdin 写死成**空输入**。该处注释自己写明了这一点，并留了话："将来若要支持 `echo x | winbash -c 'cat'`，把这里换成从 client 转发的内容即可"。

**为什么这不是"已知限制"就完事**：它**静默** —— 拿到空输出 + exit 0，调用方无从区分"文件是空的"与"输入被丢了"。这正好违反项目自己反复强调的"**不静默做错事**"承诺（README 里对 `grep -E '\d'`、`printf '%.0s'`、超时重放这几条都按这个原则处理，唯独 stdin 这条留了静默）。

**旁证**：`printf 'echo hi' | winbash.exe`（用 stdin 传**脚本**而非 `-c`）→ exit 2 `没有要执行的脚本` —— 说明 stdin 这条通道整体未被接通，不只是 `cat` 的问题。

**修的时候要探清的点**：mvdan/sh 的 `interp.StdIO` 是**构造期** Runner option，中途换不了 stdin。所以"每请求一份 stdin"要么改 `Session` 的生命周期，要么在 `interp` 层找可替换的 reader。**这是本次评估唯一没探到底的技术点**，修之前需要先做可行性验证。

### 3.2 【文档失实】README「会话级状态」清单有两项与实测不符

README 第 201 行称：`set -e`、`trap`、`alias`、变量、`cd` **都跨命令持久**。实测：

| 项 | README 声称 | 实测 |
|---|---|---|
| `set -e` / `trap` | 持久 | ✅ 持久（§2.5） |
| 变量 | 持久 | ✅ 持久（`X=hello` 下条命令可见） |
| 函数 | — | ✅ 持久（`F() {...}` 下条命令可调） |
| **`cd`** | **持久** | ❌ **不持久**：一次调用 `cd D:\work` 后 `pwd` 正确，**下一次调用 `pwd` 回到调用方目录** |
| **`alias`** | **持久** | ❌ **不持久**，且**同一次调用内**定义后立即使用也失效（`alias gg="echo hit"; gg` → 127） |

**`cd` 的成因**（`internal/daemon/daemon.go:173`）：client 每次都把自己进程的 cwd 随请求带上，daemon 先 `cd` 过去，于是覆盖了上一条命令留下的目录。**行为本身是好的**（一条命令的 `cd` 不污染下一条），但文档写反了。

**`alias` 的成因**：非交互式下 `expand_aliases` 本就没开 —— **与真 `bash -c` 一致**（对照：`bash -c 'alias gg="echo hit"; gg'` → `bash: line 1: gg: command not found`）。所以不是缺陷，但把它列进"持久"清单会让人误以为能当配置用。

**处置建议**：改 README 几行字即可，零代码风险。（本次评估未动，等确认。）

### 3.3 【架构限制】daemon 严格串行

```bash
$ 3 条并发: winbash -c 'sleep 1; echo A' & ... & wait
real 0m3.129s          # 严格串行,不是并发
```

`handle` 是逐连接串行调用的（源码注释也承认）。**单用户串行用没问题**，但若将来拿它做并行任务分发，这条会先咬人。

**为何不建议现在改**：`Session` 的变量 / cwd / 函数是**共享可变状态**，并发要重新设计隔离，而这与"会话状态跨命令持久"的语义**直接冲突**（要么放弃持久，要么给每条并发请求独立会话 —— 那就等于放弃常驻的多数收益）。属于要先定语义、再动手的改动，不该顺手做。

### 3.4 【定位偏差】① 层不比真 bash 快

| 场景 | 实测 |
|---|---|
| winbash `echo x` × 20 | **0.783s** |
| 真 `bash -c 'echo x'` × 20 | **0.689s** |

纯 bash 那层**没有速度优势**（略慢，差异在噪声量级内）。winbash 的价值集中在 ② 层与"不用换语法"，① 层的意义是**语义可控**（`ls` 永远是自己的 `ls`，不被 PATH 上重名的 Windows exe 抢走），不是快。README 的"之后每条 22 ms"自己也标注了属**早期观察**，建议不要在对外说明里当卖点。

## 4. 看着像 bug、实测正确（记下以免误改）

### 4.1 ① 层 glob 保留字面量 —— 正确，不是 bug

初看 `echo *.go` → `*.go`、`ls *.go` → 报错，很像"glob 没实现"。实测**与真 bash 一致**：

| 模式 | 结果 | 原因 |
|---|---|---|
| `*.mod` | `go.mod` | 有直接匹配 → 展开 |
| `*.go` | `*.go`（字面量） | **该目录下确实没有 `*.go`** → 无匹配保留字面量（真 bash 同） |
| `internal/*.go` | `internal/*.go` | 同上，`internal/` 下无直接 `.go` |
| `internal/*/*.go` | 58 个文件全展开 | 有匹配 |
| `internal/*/` | 10 个子目录 | 有匹配 |
| `echo *.nomatch` | `*.nomatch` | 无匹配保留字面量（真 bash 同） |

展开出的**反斜杠路径喂给 MSYS 工具也能跑**：`wc -l internal/*/*.go` → `10318 total`。`msysglob_test.go` 用两个测试钉住了这件事（`MSYS=noglob` 防 MSYS 重复展开）。**不要"修"这里。**

### 4.2 `pwsh -Version` 打印后 `$?` 显示 0 —— 是管道退出码，不是 winbash 的错

用 `winbash -c 'pwsh -Version' | head` 观察时 `$?` 为 0，单独 `>/dev/null 2>&1` 测则为 **2**。前者取的是管道末段（`head`）的退出码。winbash 的退出码是对的。
