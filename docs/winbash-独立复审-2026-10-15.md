## 3. 问题输出

### 3.1 【重要】`ls` 改用 `os.Stat` 后，每个条目多付一次系统调用

**位置**：`internal/builtins/ls.go:100-114`（`for _, name := range names { info, ierr := os.Stat(filepath.Join(abs, name)) }`）

**成因**：为把 `.` / `..` 并入统一排序，改动把"边遍历边 `e.Info()`"改成了"先 `sort.Strings(names)` 再逐个 `os.Stat`"。排序本身是对的，但**丢掉了 `DirEntry`**，于是每个真实条目都退化成一次全新的 `GetFileAttributesEx`。Windows 上 `os.ReadDir` 已经在 `WIN32_FIND_DATA` 里带回了大小与属性，`DirEntry.Info()` 直接取缓存，几乎免费。

Go 微基准（同一进程、同一目录、3000 个文件，`DirEntry.Info()` 先跑已预热系统缓存）：

```
条目数=3000
  DirEntry.Info() : 540.9µs
  os.Stat(Join)  : 2.4739735s
  比值 = 4573.81x
```

端到端印证（3000 文件目录）：

```
真 bash  ls -l : 3539 ms
winbash  ls -l : 2140 ms
winbash  ls    : 2117 ms   ← 不带 -l 付同样的代价，而 writeLsEntry 根本不用 info
```

**附带**：`long == false` 时 `writeLsEntry`(`ls.go:126-131`)只打印名字，**完全不需要 `info`** —— 这条路径上的 stat 是纯浪费。

**修改建议**：

```go
type lsEntry struct {
	name string
	info os.FileInfo
}
var items []lsEntry
if all {
	for _, n := range []string{".", ".."} {   // 只有这两个合成条目需要 os.Stat
		if fi, err := os.Stat(filepath.Join(abs, n)); err == nil {
			items = append(items, lsEntry{n, fi})
		}
	}
}
for _, e := range entries {
	if !all && strings.HasPrefix(e.Name(), ".") { continue }
	if !long {                                  // 短格式只要名字
		items = append(items, lsEntry{name: e.Name()})
		continue
	}
	if fi, err := e.Info(); err == nil {        // 走 ReadDir 的缓存
		items = append(items, lsEntry{e.Name(), fi})
	}
}
sort.Slice(items, func(i, j int) bool { return items[i].name < items[j].name })
```

**验收**：3000 文件目录上 `ls` 与 `ls -l` 的耗时从 ~2.1s 降到 <300ms；`ls -a` 排序仍与真 bash 逐字一致。

### 3.2 【建议】`firstPerlClass` 不认 `[:...:]`，`[[:alpha:]\d]` 被误判为 Perl 简写

**位置**：`internal/builtins/grep.go:339-367`（`firstPerlClass`）

**实测**（语料 `\ d ] a z - b w [ ^ 0 5`，同通道）：

```
[[:alpha:]\d]
  真 grep : 匹配 \ d a z b w           (exit 0)
  winbash : exit 2 "模式里有 Perl 简写 \d"
```

**成因**：`firstPerlClass` 只处理了 POSIX 的两条字面量规则（`[` 后紧跟 `^`；`[`/`[^` 后紧跟 `]`），**没有处理 `[:...:]`**。扫描 `[[:alpha:]\d]` 时：i=0 `[` 置 `inClass=true`；i=9 遇到 `[:alpha:]` 的收尾 `]`，`inClass` 被置回 `false`（`grep.go:363`）；于是 i=10 的 `\d` 被当成**类外**的 Perl 简写而拒收。

**为什么不能只改这一处**：`normalizeEreClasses` 有同一个盲点（它同样在 `[:alpha:]` 的 `]` 处退出 `inClass`）。若只放开拒收，`[[:alpha:]\d]` 会原样交给 `regexp.CompilePOSIX`，而 Go 把类内的 `\d` 当**数字类**，结果是匹配 `d a z b w` 而不含 `\` —— 从"响亮报错"变成"静默少匹配"，比现在更糟。

**修改建议**：把两个扫描器合成一个共用的字符类状态机（这也是回应 §三.1 里"以后应当抽"的那条，现在有了第二个反例，建议就这轮做）。状态机需同时认：`\\` 成对、`[]`/`[^]` 字面量 `]`、`[:...:]`/`[=...=]`/`[....]`、未闭合 `[`。`firstPerlClass` 与 `normalizeEreClasses` 各自调用它、取各自关心的事件。

**验收**：`[[:alpha:]\d]` 与真 grep 一致（匹配 `\ d a z b w`）；现有 8 条 golden 仍全绿；`[[:alpha:]]`、`[^]\d]`、`[]\d]` 不受影响。

### 3.3 【建议】pbb 比较测试在没有 Git Bash 的机器上整条 skip，37 条回归网静默消失

**位置**：`internal/shell/pbb_corpus_test.go:113`（`bash := findRealBash(t)`）+ 末尾 `_ = bash`

**成因**：`findRealBash`(`corpus_test.go:304-318`)在找不到 Git Bash 时调用 `t.Skip`。但 `TestPbbCorpusMatchesRealBash` **只需要已提交的 golden 表**，不需要真 bash —— 真 bash 只在 `TestUpdatePbbCorpus` 里才需要。当前写法让比较测试在不具备 Git Bash 的机器/CI 上整体跳过，而 golden 明明在盘上。

**修改建议**：`TestPbbCorpusMatchesRealBash` 删掉 `findRealBash` 调用与 `_ = bash`；把该调用留在 `TestUpdatePbbCorpus` 里。

**验收**：把 `WINBASH_REAL_BASH` 指向不存在的路径后跑该测试，37 条子用例仍执行（`--- PASS`/`FAIL`，不是 `SKIP`）。

### 3.4 【建议】pbb golden 的 `Errs` 字段从不参与比较

**位置**：`internal/shell/pbb_corpus_test.go:135`（`same := exit == want.Exit && slices.Equal(gotOut, want.Out)`）

`pbbGolden` 有 `Errs []string` 字段（`pbb_corpus_test.go:105`）且 golden 文件里也写了，但 `same` 只比 `Exit` 与 `Out`。回应 §四 特别点出 `printf '%.0s'` 那条"打了 stderr 但退出码仍是 0"是最需要盯住的形态 —— 恰恰是这一条的判据被漏掉了：stderr 变了不会失败。

**修改建议**：`same` 里加上 `slices.Equal(errs, want.Errs)`；若担心 errs 含不稳定内容（如绝对路径），可在生成侧先归一化。

**验收**：临时改一条 golden 的 `errs`，测试应失败。

### 3.5 【建议】`asExitError` 用类型断言而非 `errors.As`

**位置**：`internal/builtins/grep_classes_test.go:210-216`

```go
func asExitError(err error, target **exec.ExitError) bool {
	if ee, ok := err.(*exec.ExitError); ok { ... }
```

`cmd.Run()` 返回的错误在 Go 1.20+ 可能是包装过的；`errors.As` 更稳，也不需要这个辅助函数（直接 `errors.As(err, &ee)`）。同文件其余部分质量很高，这一处是与整体水准不一致的小瑕疵。

### 3.6 【建议】`cleanBashEnv` 与 `cleanCorpusEnv` 是逐字重复的两份实现

**位置**：`internal/builtins/grep_classes_test.go:192-204` 与 `internal/shell/corpus_test.go:355-368`（两条 `for` 循环体完全相同）

两者分属不同包，无法直接共用；但"哪些环境项会让参照 bash 不再可信"是**一条规则**，两份就会有一份先漂移。建议挪到一个测试辅助包（例如 `internal/errs` 之外新建 `internal/testenv`，只有 `_test.go` 也可）。

### 3.7 【建议 / 需确认】golden 再生成没有固定 MSYS 与 locale 通道

**位置**：`internal/builtins/grep_classes_test.go:102-108`（`exec.Command(bash, "-c", "grep -E "+..." chars.txt")` + `cleanBashEnv()`）

**依据**：本轮定位 §4.1 分歧时实测到，GNU grep 3.0 对**类内 `\`** 的处理会随调用通道改变 —— 同一份字节的 pattern，经 `-f` 读入与经 argv 传入给出不同结果；同一个 exe 由不同 MSYS 根启动也给出不同结果（详见 §4.1）。也就是说"真 grep 给什么"在本机上不是通道无关的。

因此 `cleanCorpusEnv`/`cleanBashEnv` 只滤了 `BASH_ENV`/`ENV`/`BASH_FUNC_*` 还不够：`MSYS2_ARG_CONV_EXCL`、`MSYS_NO_PATHCONV`、`MSYSTEM`、`LC_*`、`LANG`、`GREP_OPTIONS` 都可能参与。当前 golden 是**已提交的事实**，比较测试不受影响；风险只在**下次 `-update-grep-golden` 在另一台机器上跑**时把另一种语义写进去。

**修改建议**（择一，成本低）：
- 生成时把 `MSYS2_ARG_CONV_EXCL`、`MSYS_NO_PATHCONV`、`MSYSTEM`、`LC_ALL`、`LANG`、`GREP_OPTIONS` 一并固定成显式值；或
- 在 golden 文件头部记录生成时的通道（`bash --version` + MSYS 变量 + 一条 `[\d]` 的自检结果），让"换了通道"这件事显式可见。

**需确认**：我只在**本机**观察到通道相关性，不能断定它在其他 MSYS 版本上同样成立。因此这条标"建议"而非"重要"。

## 4. 争议处理

### 4.1 【我上一轮错了，回应是对的】`[\d]` 那一列

**分歧点**：上一轮我写"真 GNU grep 把类内的 `\` 当转义引导符，`\d` 退化成 `d`，只匹配 `d`"；回应写"实测真 grep 匹配 `\` 与 `d`"。

**判断依据（本轮重新测量，四种通道互证）**：

| 通道 | `[\d]` 的结果 |
|---|---|
| 我的 shell 直接调 `/c/Program Files/Git/usr/bin/grep.exe` | `d` |
| Git Bash 里调同一个 exe | `\` `d` |
| Python `subprocess` 传 argv（不经 shell） | 两次运行结果**互相矛盾**（一次 `d`、一次 `\d`） |
| 同一 shell 内、`-f` 读入与 argv 传入对比 | 两者**互相矛盾** |

四个通道无法自洽，说明**至少一层在改动反斜杠**，任何单通道结果都不可信。于是我改用**同通道对照**——真 grep 与 winbash 都从 Git Bash 里、用同样的单引号引用跑同一份语料：

```
  OK    [\d]     -> [\d]          OK    [\]]     -> []      (exit 1)
  OK    [\w]     -> [\w]          OK    [\\d]    -> [\d]
  OK    [a\-z]   -> [\d]azbw^]    OK    [\\]     -> [\]
  OK    [\[]     -> [\[]          OK    [a-c]    -> [ab]
```

8/8 一致。扩大到 20 条后 19/20 一致（唯一偏差是 §3.2 的 `[[:alpha:]\d]`）。

**结论**：真 grep 对 `[\d]` 给 `\` 与 `d`——**回应是对的，我上一轮那列是错的**。错因是我的 harness 在把 `'[\d]'` 交给 grep 时改动了反斜杠（同一环境下 `-f` 与 argv 结果不同即为证据）。我在上一轮把它写成"实测"，是**把一次未受控的测量当成了事实**，这一点我认。

**取舍说明**：我上一轮同时指出的 `[\\d]` / `[\\]` 两条**仍然成立且已被修好**（同通道验证：修前 exit 2，现在 `[\\d]`→`\ d`、`[\\]`→`\`，与真 grep 一致）。所以正确的拆分是：**根因与那两条真回归成立；"`[\d]` 的方向错了"这一条不成立**。回应的 §1.2 也是这么拆的，我认同。

### 4.2 【分歧，各对一半】`BASH_ENV` / `BASH_FUNC_*` 是否"在本机不存在"

回应 §2.1 写"本机实测 BASH_ENV=(空)、BASH_FUNC_*=0 个"。**在本次复审所处的环境里不是这样**：

```
BASH_ENV=[D:\tools\WorkBuddy\...\shim\safe-bin\safe-delete-bash-env.sh]
BASH_FUNC_rm%% / BASH_FUNC_unlink%% / BASH_FUNC_rmdir%%   (3 个)
```

且**同一环境下**：上一轮 `go test ./...` FAIL 3 条语料 → 本轮加入 `cleanCorpusEnv()` 后 **10 包全绿**。这个红→绿发生在同一台机器、同一个 shell，只能归因于环境过滤生效。

**结论**：垫片的**存在性判断**回应不准确（至少不适用于本环境），但**加固决定是对的且已生效**；我上一轮把"加固建议"和"本机必然红"绑在一起，措辞也过强（应写成"在这类环境下"）。两边各让一步：事实是本环境有垫片，价值是过滤本身。

### 4.3 【回应是对的】`client` 覆盖率的措辞

回应指出我"正文写了'不能据此说修复没被测试'，但 §5 清单仍按'覆盖率掉了'列"。**这个批评成立**，是我报告内部不一致。本轮的实测也印证了回应的口径：`client` 包内 20.7%，而跨包口径下 `oneShot` / `isTimeout` 是被覆盖的。我上一轮的清单条目应改写为"补 `readEndpoint` / `forgetStaleEndpoint` 的单测"，而不是"覆盖率掉了"。
