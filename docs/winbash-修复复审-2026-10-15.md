### 1.1 P0-1 鉴权：真修好了（我亲自复现了攻击）

我没有采信代码阅读，而是重建二进制后用 Python 裸 socket 打四条路径：

## 二、新引入的 bug（按严重度）

### 2.1 🔴 P1：`normalizeEreClasses` 修错了，并引入 4 类回归

这是本次复审**最重要**的发现。我没有停留在代码阅读，而是临时写了一个探针（跑完已删除），用**仓库里真实的** `normalizeEreClasses` 与 `regexp.CompilePOSIX` 做前后对照，语料是"一字符一行"，这样匹配结果本身就是字符集合：

| pattern | 改写前（旧代码） | 改写后（新代码） | 真 GNU grep -E |
|---|---|---|---|
| `[\\d]` | `\` `d` ✅ | **编译失败** 🔴 | `\` `d` |
| `[\\]` | `\` ✅ | **编译失败** 🔴 | `\` |
| `[\]]` | `]` ✅ | **静默无匹配** 🔴 | `]` |
| `[\d]` | 响亮报错 exit 2 | `\` `d` ⚠️ | `d` |
| `[\w]` | 响亮报错 exit 2 | `\` `w` ⚠️ | `w` |
| `[a\-z]` | `a` `z` `-` | `a b z \ ] _ d w` 🔴 假阳性 | `a b z d w` |
| `[\-a]` | `a` `-` | `a \ ] _` 🔴 假阳性 | `a` `-` |
| `[\[]` | `[` | `\` `[` 🔴 假阳性 | `[` |

**三类根因：**

1. **对已转义的 `\\` 又转义了一次。** 扫描器把 `\X` 无条件改写成 `\\X`，于是在 `[\\]` 上先吃掉了 `\\` 又把 `]` 吞进 payload，输出 `[\\\]`——未闭合。`[\]]` 同理，变成"反斜杠后跟 `]`"这个空集合，**静默**返回无匹配（exit 1，看起来像"真的没有匹配"）。
2. **两个扫描器对同一份语法的理解不一致。** 同一提交里新增的 `firstPerlClass`（`grep.go:301`）**认得** POSIX「`[` 或 `[^` 后紧跟的 `]` 是字面量」这条规则（`grep.go:322-328` 显式处理了），而 `normalizeEreClasses` 完全不认。同一个包里两份对字符类的状态机，规则却不一样——这本身就是 bug 温床。
3. **"类内 `\` 是字面量"这个判断来自规范文本，但真 GNU grep 不这么干。** 实测 `grep -E '[\d]'` 在真 bash 里匹配 `d`（GNU 把类内的 `\` 当转义引导符，`\d` 退化成 `d`）。项目立身之本是"与真 Git Bash 对齐"，而 README 新增的那一行还写着"支持，按 ERE 原意匹配「反斜杠或字母 d」"——这等于把一个**已知会与 bash 不一致**的行为写进了"已知差异"表，但同时把原来的"响亮报错"换成了"哑的错答案"。**这正是本项目最想消灭的形态**（`classify.go` / `shell.go` 里那些 `rejectProcessSubstitution`、`rejectUnsupportedParamExpansion` 的注释反复在讲这件事）。

顺带：`[a\-z]` 那类让**假阳性**从"少匹配"变成"多匹配"。对 grep 而言，多匹配比少匹配更危险——AI 会拿到并不存在的行。

**修复思路（二选一，并配套机器生成的 golden）**

- **甲（推荐，与真 grep 对齐）**：类内 `\X` 按 GNU 语义**去转义**，不是加倍。即：若 `X` 是 Go 类内元字符（`]`、`\`、`^`）则输出 `\X` 保留转义，否则输出裸 `X`。效果自检：

  | pattern | 归一化后 | 与真 grep |
  |---|---|---|
  | `[\d]` | `[d]` | ✅ |
  | `[\\d]` | `[\\d]`（不碰） | ✅ |
  | `[\\]` | `[\\]`（不碰） | ✅ |
  | `[\]]` | `[\]]`（不碰） | ✅ |
  | `[a\-z]` | `[a-z]` | ✅ |
  | `[\[]` | `[[]` | ✅ |

  关键改动：先**成对消费** `\\`（已转义的转义不再处理），再处理 `\X`；并且 `[]`/`[^]` 开头字面量规则要与 `firstPerlClass` 共用同一段状态机（抽一个 `classScan` 出来，两处调用）。

- **乙（保守，如果暂时不想复刻 GNU）**：把归一化撤掉，回到"类内带 `\` 一律明确报错 + 给 POSIX 替代写法"。响亮错误是可恢复的，静默错答案不是。**在没有机器生成的 golden 之前，乙比现在的状态更安全。**

- **无论选哪条**：把一个表驱动用例加进 `builtins` 测试，把上面 7 个 pattern 的**真 grep 输出**钉住（期望值从真 grep 产出、机器生成，不要手写）。现在 `normalizeEreClasses` 有 80% 覆盖却没人测这几个形状——覆盖率在这里骗了人。

### 2.2 🔴 P1：`cat -n` 多文件编号不连续

`cat.go:114` 的 `copyCat` 把行号计数器 `n` 放在**局部变量**里，于是每个文件从 1 重新开始。实测：

```
$ cat -n f1.txt f2.txt        # f1=(a,b) f2=(c,d)
真 bash :      1 a |      2 b |      3 c |      4 d     ← 跨文件累加
winbash :      1 a |      2 b |      1 c |      2 d     ← 每个文件重置
```

`cat -n f1.txt - < f2.txt` 同样错。GNU cat 的行号是**跨文件累加**的。

**修法**：把计数器提到 `Cat` 里，`copyCat(out, r, numbered, &n)`，或让 `copyCat` 返回本次消耗的行数由调用方累加。约 3 行改动。

**注**：其余细节是对的——`%6d<TAB>` 格式与 bash 逐字一致；末行无换行时不补 `\n`（实测 `cat -n f3.txt` 给 `     1\tno-newline` ✅）；用 `bufio.ReadBytes` 而不是 `Scanner`，**没有踩 64KB 行上限那个经典坑**（这点比很多实现都做得好）。

### 2.3 🟡 P2：`ls -a` 的 `.`/`..` 硬编码排在最前

`ls.go:85-95` 先把 `.` 与 `..` 写出去，再写 `ReadDir` 的条目（后面才是排序的）。于是只要目录里有**排序在 `.`(0x2E) 之前**的名字（`!` `#` `$` `%` `&` `'` `(` `)` `*` `+` `,` `-`），顺序就与 bash 不一致：

```
目录含 !x / .hidden / zz.txt
真 bash : !x | . | .. | .hidden | zz.txt     ← 所有名字一起排序
winbash : . | .. | !x | .hidden | zz.txt     ← . 和 .. 恒在最前
```

**修法**：把 `.`、`..` 塞进同一个待排序列表再统一 `sort`。这条不是本次引入的（原来就有），但本次既然动了点文件这块，正好一起收掉。

### 2.4 🟡 P2：语料测试的 oracle 被宿主环境污染 —— `go test ./...` 目前是**红的**

`go test ./...` 在本机 **FAIL 3 条**，全在 `TestBashCorpusMatchesRealBash`：

```
script : echo hi > "WBTMP/wb-corpus-1.txt"; cat ...; rm -f "WBTMP/wb-corpus-1.txt"
bash   : exit=1 out="hi"      ← 真 bash 说 rm 失败了
winbash: exit=0 out="hi"      ← winbash 说成功
```

**根因（我逐层剥出来的，不是猜的）**：

```
环境里注入了：BASH_ENV=...\safe-delete-bash-env.sh
              BASH_FUNC_rm%%  BASH_FUNC_rmdir%%  BASH_FUNC_unlink%%
```

参考 bash 的 `rm` 被替换成一个"移到回收站"的 bash 函数（导出函数走 `BASH_FUNC_*` 环境变量传递）。该垫片在**Windows 风格路径**上失败并 fail-closed 返回 1 —— 而语料现在喂给它的正是 `filepath.ToSlash(t.TempDir())` 给出的形状（`C:/Users/...`）。

三条对照实验：

| 条件 | 结果 |
|---|---|
| 原样（现状） | `rm` → exit 1 ❌ |
| 只裁 `BASH_ENV` | **仍然 exit 1**（因为垫片是从 `BASH_FUNC_*` 传进来的，裁 `BASH_ENV` 不够） |
| 裁 `BASH_ENV` + `BASH_FUNC_*` | **exit 0** ✅ |

**为什么这条重要**：一个差分测试的价值完全取决于参照物的可信度。参照物被宿主环境改写之后，"与真 bash 一致"就不再是一个事实断言。任何装了同类垫片的环境（CI、其他 agent 沙箱）都会红，而失败信息（`bash exit=1`）会把人引向"winbash 的 rm 行为不对"——**误导性极强**。

**修法（已验证有效）**：`runRealBash` 给子进程一个**显式环境**——从 `os.Environ()` 里滤掉 `BASH_ENV`、`ENV` 和所有 `BASH_FUNC_` 前缀项。为对称，winbash 侧也过滤（它本来不读 `BASH_ENV`，但让"两边环境一致"这个意图显式化）。

**同时**：`docs/superpowers/plans/2026-10-13-winbash.md` 里写着"`go test ./...` 全绿"——在本机不成立。要么修掉环境问题，要么把这句改成有条件的表述（"在无 `BASH_ENV`/`BASH_FUNC_*` 的干净环境下全绿"）。**一个声称全绿的测试套件实际是红的，比一条已知失败更伤信任。**

**另外要替作者说清楚**：把语料文件从**包源码目录**挪到 `t.TempDir()`（`corpus_test.go:33-37`）是**修对了**——原审计的风险（用例的 `rm` 失败就在仓库里留垃圾、且诊断信息完全看不到）确实被消掉了。而把 `known` 从"两边一致就 Skip、其余直接 return"改成"**断言差异仍然存在**（`t.Errorf`）"（`corpus_test.go:45-54`）是本次改动里第二个高价值改进：原审计指出 `known` 条目是"不做任何检查的空壳"，现在一条过期的 `known` 会自己浮出来。这两条我完全认同。

## 三、更多评测方面（本次复审新增的维度）

原审计覆盖了功能、性能、代码质量、可扩展性、安全、错误处理六维。这次复审再补七个维度：

### 3.1 语义等价性 / 差分一致性（权重最高，也是本次唯一失手的地方）

**方法**：把"真 Git Bash"当 oracle，构造能暴露差异的最小语料（一字符一行 → 匹配集合即字符集合），逐 pattern 对照；对可疑改动用仓库真实函数做**前后对照**而不是只看最终状态。

**发现**：`grep -E` 字符类（§2.1）、`cat -n`（§2.2）、`ls -a` 排序（§2.3）、`grep` flag 不排列（`grep -l b . -r` 真 bash 能跑、winbash 把 `-r` 当路径）——四项。前三项中两项是本次引入的。

**这条维度的价值**：仓库自称"与真 Git Bash 逐条语料对照"，而语料是**手写的期望值**。手写期望值只能覆盖作者想到的形状；**一字符一行的字符集合语料 + 真 grep 作为 oracle** 能自动覆盖作者没想到的形状——它一次就抓出了 9 个 pattern 里的 7 个偏差。

### 3.2 测试可信度（不只看百分比，要看**归属口径**与 oracle）

**覆盖率有两种口径，数字差别很大，不能用错**：

| 包内（`go test ./... -coverprofile`） | 0.0% | 0.0% | 0.0% | 69.4% |
| 跨包（`-coverpkg=./...`） | 58.6% | 100% | 100% | 75.8% |

**这个差别很重要，我要纠正一个容易下的错误结论**：`oneShot` / `isTimeout` / `pwsh.Dead` 在包内口径是 0%，但**它们的行为确实被测了**——`guard_test.go` 在 `daemon` 包里跑 `client.Run`，跨包口径立刻显现。**不能据此说"修复没被测试"。**

但反过来，**有两个函数在两种口径下都是 0%**，且都是本次新增：

| 函数 | 位置 | 职责 | 两种口径 |
|---|---|---|---|
| `retryAfterAuthFailure` | `client.go:158` | 鉴权失败后重读端口文件重试 | **0% / 0%** |
| `forgetStaleEndpoint` | `client.go:211` | "不是自己的地址就别删"的竞态保护 | **0% / 0%** |

前者是本次新写的鉴权重试逻辑，后者是防"删掉新 daemon 端口文件"的竞态护栏——**都无回归网**。另外 `ensureDaemon` 跨包只有 20%，`dial` 23%。

`spawnDaemon`（`client.go:296`）在两种口径下都是 0%，但**这是数字骗人**：它只在被拉起的子进程里跑，Go 覆盖率不回传。`cmd/winbash/e2e_test.go:87 TestDaemonIsReusedAcrossClientProcesses` 用真 exe、fresh endpoint、连续 4 次断言 pid 不变，**确实端到端覆盖了冷启动路径**。作者自己也在 `main_test.go:40` 的注释里诚实记账了这件事。这条我要替作者说清楚。

**建议**（成本极低，都是纯函数/纯文件级，不需要网络）：
- `readEndpoint`（`client.go:279`）的两行解析：只有一行、空文件、token 缺失；
- `forgetStaleEndpoint`：地址匹配才删 / 不匹配不删；
- `retryAfterAuthFailure`：重读后成功 / 重读后仍失败原样上抛。

**已知诚实的缺口**（不必现在补，但账要记着）：`retryAfterAuthFailure` 与 `forgetStaleEndpoint` 是竞态路径，真要覆盖得用"两个 daemon 抢同一个端口文件"的时序构造，属于集成测试范畴。

### 3.4 安全边界与威胁模型表述

不只是"有没有洞"，还要看**承诺的边界是否诚实**。`ipc.go:18-23` + README「安全边界」段的表述是本次改动里最成熟的部分：主动写明 token 挡不住同用户进程、端口文件可被改写、`icacls` 失败时"只警告不改成败，而使用者有权知道"。

**残留加固项**（都不到 P1，但属于同一类问题的延伸）：
- `writeResponse`（`daemon.go:192`）**没有写超时**。客户端发完合法请求后不读响应，daemon 会阻塞在 write 上直到 TCP 超时——这正是 P0-2 想消灭的"一条连接拖住串行 handle"的同类，只是这次需要持有 token（同用户），所以只算加固项。建议 `conn.SetWriteDeadline`。
- `icacls` 每次 `Serve` 都同步 fork 一个进程。因为端口文件在 `icacls` **之前**就已写好（`daemon.go:65` → `daemon.go:69`），client 不会被它挡住 ✅ 设计是对的；但如果以后把写文件挪到收紧之后，会引入一次可观测的冷启动延迟。

### 3.5 文档–实现一致性

**改对了的**：README 新增的「性能怎么量」段是**对自己此前过度声明的正面纠正**——明确写"首次 70ms / 之后 22ms 属于早期观察，既难证实也难证伪"，并给出可复现的进程内 benchmark。我复现了：`echo` **7.8µs/op**、`echo hello | grep hell` **152µs/op**（README 写 6.4µs / 119µs，同量级，差异来自机器负载）。这种"把不可验证的数字降级为早期观察、同时给出可验证的替代"是正确做法。

**仍有落差的**：
- §2.4：计划文档写"`go test ./...` 全绿"，实际红 3 条。
- §2.1：README 新增行"`grep -E '[\d]'` **支持**，按 ERE 原意匹配「反斜杠或字母 d」"——与真 grep 不一致（真 grep 匹配 `d`），且它**没有覆盖**被连带改坏的 `[\\]` / `[\\d]` / `[\]]`。
- `--timeout` 在**嵌套模式**下被静默忽略：`client.go:51` 的 `runLocal(script, jsonOut)` 收不到 timeout，`runLocal` 用 `context.Background()`（`client.go:334`）。README 说 `--timeout` 是"单次请求超时"，嵌套里实际不生效。低危（嵌套非热路径），但属于"文档说了、实现没做"。

### 3.6 向后兼容性 / 协议演进

- `ipc.Request.Token` 用了 `omitempty`，`Response.Auth` 也 `omitempty` → 新旧版本的帧互相**可解析** ✅
- `client.readEndpoint` 对"只有一行、没有 token"的文件的处理是"token 当空串 → daemon 侧拒绝"，注释写明"缺少凭据应该是**被拒**，不是**放行**"（`client.go:276-278`）——这是正确的降级方向 ✅
- ⚠️ **没有协议版本号**。原审计就提过。目前靠"字段可选 + 缺凭据拒绝"兜住了，但如果以后要改帧格式（例如加流式输出），旧 client 连新 daemon 会得到难懂的错误。属于演进期要补的账，不是现在的 bug。

### 3.7 可观测性与可调试性

- `--status` 现在能报 `pid` / `cwd` / `addr` / ② 层引擎状态（`daemon.go:157`）✅
- ② 层启动失败时附 `pwsh stderr` 尾部 8KB（`pwsh.go:313` 的 `hint()`）——"没有窗口 + stderr 直接丢弃 = 启动失败完全静默"，这个兜底很实用 ✅
- `restrictEndpointFile` 失败时往 stderr 打一行警告（`daemon.go:240-243`）✅
- ⚠️ 缺口：daemon 是脱离窗口启动的（`spawnDaemon` 用 `CREATE_NO_WINDOW`），它的 stderr 实际上**没人看**。`restrictEndpointFile` 的警告、`pwsh` 的启动线索都写进这个黑洞。建议把 daemon 的 stderr 重定向到一个 `%TEMP%\winbash-<user>.log`，出错时用户/agent 至少有一条路。

### 3.8 认知负荷与可维护性

- `normalizeEreClasses` 与 `firstPerlClass` 是**两份对字符类的状态机**，规则不一致（§2.1 根因 2）——这是可维护性上最值得注意的一处。抽一个共用的 `classScan` 能同时消掉一类 bug 和一份认知负担。
- `daemon.go` 的注释密度很高但都有实测支撑，不构成负担。
- `output.go` 删掉两个函数后包注释仍留了一大段解释"值保证在哪实现"——**保留了**，这是对的（它解释了为什么 Go 侧没有兜底），比删掉注释好。

## 六、总体评估

**一句话**：这次修复在**安全**与**"不静默做错事"**两条主线上是真的到位了——P0/P1 五条我一条条复现验证过，机制正确、测试是真测、注释带实测证据。尤其是三处判断显示了成熟的工程判断力：**超时不重试但鉴权失败可以重试**（区分"已执行"与"未执行"）、**`Dead` 单向失效而由持有者负责重建缓存**、**删掉"读代码的人以为存在"的假兜底**。

失手集中在一处：`grep -E` 字符类归一化。它的问题不在于"选错了语义"，而在于**三个具体实现的疏漏（重复转义 `\\`、不认 `[]`/`[^]` 字面量规则、与同包另一份扫描器规则不一致）把改动变成了"响亮的错 → 哑的错"**，方向和项目的底线相反。这个模式值得记下来：**当"按规范推理"与"按参照实现实测"冲突时，在一个以"与参照实现对齐"为卖点的项目里，实测必须赢**——否则就该响亮地拒绝，而不是安静地给出不同的答案。

**从 68.3% 到 69.4% 的覆盖率提升看起来不大，但结构上的变化是实质的**：`cmd/winbash` 0% → 88.7% 消掉了一个整包盲区；`known` 从空壳变成"断言差异仍存在"让语料表重新有了自我修正能力；`bench_test.go` 把不可验证的性能宣称换成了可复现的数。这三条比百分比更有价值。

**下一步**：先修 P1 两条（都是几行到几十行的改动，且都有明确的对照验证手段），再修语料 oracle 让 `go test ./...` 真正变绿——**一个红的测试套件会让所有"有测试钉住"的声明失去分量**，这比多修一个 bug 更影响项目的可信度。
